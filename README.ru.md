# gc2607-isp

*English version: [README.md](README.md).*

> **Статус: тестирование / экспериментальный.** Рассчитан на одно конкретное
> устройство (MateBook X Pro 2024, GC2607); работает сквозным образом на машине
> разработки, но интерфейсы, значения по умолчанию и тюнинг ещё могут меняться.

Software ISP (image signal processor) на Rust для встроенной цветной камеры
GalaxyCore GC2607 ноутбука Huawei MateBook X Pro 2024 (Intel Meteor Lake, IPU6)
на Linux. Превращает сырой Bayer-кадр сенсора в цветное изображение, используя
извлечённый тюнинг сенсора.

**Качество изображения — главная цель**: смысл проекта в том, чтобы получить
картинку лучше, чем даёт обобщённый software ISP (см. [Возможности](#возможности)
и [Назначение](#назначение)).

В ноутбуке два сенсора GalaxyCore. Этот проект управляет только фронтальной
**цветной** камерой **GC2607** (ACPI `GCTI2607`). Второй, **GC1029** (ACPI
`GCTI1029`), — отдельный **инфракрасный** сенсор (Windows Hello) на другой шине
I2C; для цветной веб-камеры он **не нужен**, Linux-драйвера здесь не имеет и не
затрагивается.

## Назначение

SoftISP в составе libcamera даёт пригодное, но посредственное изображение:
простой debayer, остаточный grey-world-оттенок AWB, отсутствие коррекции
виньетирования. Этот проект реализует собственный CPU-конвейер на извлечённом
тюнинге сенсора (матрицы цветокоррекции, карты lens-shading, локус белого),
которого у тюнинга libcamera нет.

## Возможности

Главная цель — качество изображения; всё перечисленное служит ей, при этом
производительность и энергопотребление удерживаются в рамках, чтобы проект был
пригоден как повседневная веб-камера на тонком ноутбуке.

**Обработка изображения** (заводской тюнинг под конкретный экземпляр, см.
[Источник тюнинга](#источник-тюнинга)):

- вычитание чёрного уровня и поканальная (по Bayer-каналам) **коррекция
  lens-shading** с выбором источника света по сцене (сильное виньетирование,
  усиление до ~5.5x);
- **робастно-нейтральный автоматический баланс белого** (медиана цветности по
  ярким неклиппированным пикселям) с оценкой цветовой температуры относительно
  локуса белого сенсора;
- **полноразрешающий debayer Malvar-He-Cutler** (собственная построчно-параллельная
  реализация), плюс облегчённый half-res-режим;
- **посекторная по тону цветокоррекция**: 5 матриц CCM, интерполируемых по CCT,
  уточняемых 24 матрицами по секторам тона, затухающими к глобальной матрице
  вблизи нейтрали;
- **коррекция боковой хроматической аберрации**;
- **gain-адаптивное шумоподавление**: box-blur по цветности + временное по яркости
  (IIR с гейтом движения), включается только по мере роста аналогового усиления
  при слабом освещении;
- вывод с гаммой sRGB, упаковка YUYV 4:2:2.

**Автоэкспозиция**: петля exposure-priority управляет exposure/gain/vblank прямо
на сенсоре через V4L2-субдев, измеряя среднюю яркость готового кадра в линейном
свете (без зависимости от AGC libcamera).

**GPU-бэкенд**: пиксельные стадии выполняются как compute-шейдеры Vulkan (wgpu,
Mesa ANV на Intel iGPU), проверены на совпадение с CPU-путём с точностью до 1 LSB;
`--backend auto` предпочитает GPU и снижает потребление CPU процессом примерно в
4 раза при той же частоте кадров.

**Захват по запросу**: камера открывается и ISP работает только пока приложение
ведёт захват (событие client-usage у v4l2loopback); в простое сенсор остаётся в
runtime-suspend.

**Интеграция**: GC2607 выбирается по имени `Model` в libcamera, а не по индексу
перечисления, поэтому находится корректно даже при наличии другой камеры
(например, подключённой USB-веб-камеры). Вывод — узел v4l2loopback, который
открывает любое веб-камерное приложение (браузер, OBS, `ffplay`); светодиод
приватности загорается автоматически во время стрима (обрабатывается ядром V4L2 /
INT3472), а физический боковой переключатель камеры ноутбука учитывается (при
выключенном переключателе сенсор не выдаёт пригодного кадра). Офлайн-CLI
конвертирует сохранённый сырой кадр в PNG/PPM на любой машине.

## Архитектура: стек камеры

Этот ISP — одно из звеньев цепочки от сырого сенсора до обычного узла
веб-камеры. Каждый слой ниже передаёт данные следующему:

```
GC2607 sensor (MIPI CSI-2, I2C control)
  -> gc2607.ko              V4L2-субдев-драйвер: стриминг + контролы exposure/gain/vblank, runtime PM
  -> ipu-bridge (patched)   привязывает сенсор GCTI2607 к Intel IPU6 (clock через ACPI/_DSM + таблица моста)
  -> intel_ipu6 / ipu6-isys приёмник CSI-2 у IPU6: отдаёт сырой Bayer-кадр, создаёт узлы V4L2 capture + subdev
  -> libcamera (0.7)        перечисляет конвейер IPU6 + сенсор gc2607; используется ТОЛЬКО для получения сырого потока
  -> gc2607-video (this)    ISP: сырой Bayer -> цветной YUYV (CPU или GPU); AE управляет сенсором через V4L2-субдев
  -> v4l2loopback           этот бинарь — producer; узел loopback выглядит как обычная веб-камера
  -> application            браузер / OBS / ffplay открывает /dev/videoN
```

Два момента требуют пояснения: почему цветная обработка вынесена в отдельный
бинарь, а не выполняется собственным ISP libcamera, и почему кадры попадают в
приложения через v4l2loopback, а не через элемент GStreamer.

### Почему собственный ISP, а не SoftISP libcamera

В составе libcamera есть software ISP (конвейер «simple» / soft) для сенсоров
без аппаратного ISP. Он намеренно минимален: базовый debayer, grey-world-AWB,
гамма, и предоставляет только контролы Gamma/Contrast/Saturation. Он не может
применить заводской тюнинг под конкретный экземпляр, на котором держится
качество изображения этого проекта:

- 5 матриц цветокоррекции, интерполируемых по цветовой температуре, плюс 24
  матрицы по секторам тона (см. [Конвейер обработки](#конвейер-обработки) и
  [Источник тюнинга](#источник-тюнинга));
- поканальную коррекцию lens-shading с выбором источника света;
- коррекцию боковой хроматической аберрации;
- gain-зависимое шумоподавление по цветности/яркости;
- GPU-бэкенд (Vulkan) для пиксельных стадий.

Кроме того, у него нет пути ручной экспозиции: в raw-режиме IPA libcamera не
выполняется, а контролы запроса отбрасываются, поэтому собственная петля
автоэкспозиции не может пройти через него. Поэтому проект использует libcamera
**только как API сырого захвата** и управляет exposure/gain/vblank напрямую через
V4L2-субдев ([src/sensor.rs](src/sensor.rs)), параллельно сырому потоку libcamera.

### Почему ISP не встроен в libcamera или GStreamer

В принципе обработка могла бы жить внутри libcamera (как расширение soft-IPA) или
внутри элемента GStreamer. Ни то, ни другое не сделано — намеренно:

- **Внутри libcamera** означало бы форк SimplePipelineHandler и его soft-IPA (C++)
  и отслеживание их внутреннего API между релизами. Интерфейс IPA не предназначен
  для размещения внешнего конвейера с бэкендом wgpu/Vulkan; стоимость
  сопровождения высока, и это привязало бы проект к одной версии libcamera.
- **Как элемент GStreamer** означало бы либо использование `libcamerasrc` (который
  идёт через отвергнутый выше soft ISP), либо написание и поставку собственного
  плагина GStreamer, оборачивающего Rust-ISP. Это лишняя поверхность без выгоды
  здесь: бинарь уже выдаёт готовые YUYV-кадры, поэтому пишет их напрямую в узел
  v4l2loopback, который любое веб-камерное приложение открывает без плагина.

### Отношение к v4l2-relayd

[v4l2-relayd](https://github.com/9elements/v4l2-relayd) — это вспомогательный
сервис Ubuntu/IPU6, который по запросу наполняет узел v4l2loopback из источника
GStreamer. Как producer здесь он не используется по той же причине: его
источник — конвейер GStreamer, который обошёл бы этот ISP. Однако его **механизм
работы по запросу** — событие `V4L2_EVENT_PRI_CLIENT_USAGE` у v4l2loopback,
срабатывающее при начале или прекращении захвата приложением, — это правильный
способ включать камеру только во время использования, и он применён прямо внутри
`gc2607-video` (флаг `--on-demand`), а не через запуск relayd (см.
[План развития](#план-развития)).

## Конвейер обработки

```
raw SGRBG10 (1928x1088)
  -> BLC          вычитание чёрного уровня (пьедестал 64)
  -> LSC          поканальная коррекция виньетирования (источник света по сцене)
  -> AWB          робастно-нейтральный: медиана цветности ярких неклиппированных пикселей
  -> debayer      half-res (стадия 1); full-res MHC (стадия 2)
  -> CCM          посекторная по тону цветокоррекция (24 сектора), интерполяция по CCT
  -> sRGB gamma
  -> RGB8
```

Баланс белого, CCT и источник света для lens-shading оцениваются на кадре после
BLC, до применения LSC.

Цветовой шаг секторирован по тону: помимо единственной глобальной матрицы, 24
матрицы по тону уточняют коррекцию по тону цвета, затухая к глобальной матрице
вблизи нейтрали. См. [docs/acm-color-model.md](docs/acm-color-model.md).

## Источник тюнинга

Тюнинг разбирается из файла тюнинга камеры `.aiqb`:

- **CCM** — 5 матриц цветокоррекции по CCT (2963/3803/4049/4779/6426 K), плюс
  локус белого для оценки CCT. Файл [data/gc2607_ccms.json](data/gc2607_ccms.json).
- **ACM** — 24 матрицы по секторам тона для каждой из 5 CCT (посекторное по тону
  уточнение CCM). Файл [data/gc2607_acm.npz](data/gc2607_acm.npz); см.
  [docs/acm-color-model.md](docs/acm-color-model.md).
- **LSC** — 5 источников света x 4 Bayer-канала x сетка 63x47, усиление 1.0..5.543
  (сильное виньетирование). Файл [data/gc2607_lsc.npz](data/gc2607_lsc.npz).
- **LCA** — сетки сдвига боковой хроматической аберрации (red/blue относительно
  green). Файл [data/gc2607_lca.npz](data/gc2607_lca.npz).

Тоновая кривая не извлекается (разбирается закрытым парсером Intel), поэтому
используется стандартная гамма sRGB.

Данные для Rust генерируются из источников скриптом
[tools/gen_tuning.py](tools/gen_tuning.py) (создаёт
[src/tuning_data.rs](src/tuning_data.rs) и `data/lsc_grids.bin`).

## Установка (Ubuntu 26.04)

Цветной веб-камере нужны все три части стека
([Архитектура](#архитектура-стек-камеры)): драйвер сенсора `gc2607`,
пропатченный `ipu-bridge` и этот ISP. Каждая публикуется как Debian-пакет на
странице релизов своего проекта на GitHub. Самый быстрый путь на Ubuntu 26.04 —
установить три готовых пакета; сборка всего из исходников тоже поддерживается
([Сборка из исходников](#сборка-из-исходников)).

Проект рассчитан именно на MateBook X Pro 2024 и проверен на Ubuntu 26.04 с
ядром серии 7.x.

### Готовые пакеты

Предусловия:

- Ubuntu 26.04 с ядром серии 7.x и соответствующими заголовками ядра
  (`linux-headers-$(uname -r)`), которые нужны DKMS для сборки модулей.
- Физический боковой переключатель камеры на корпусе ноутбука должен быть
  **включён**, иначе сенсор не выдаёт пригодного кадра.
- При включённом Secure Boot DKMS подписывает модули локальным ключом MOK и
  предлагает зарегистрировать его при первой сборке; завершите регистрацию
  (после перезагрузки система попросит подтвердить ключ), чтобы подписанные
  модули загружались.

1. Скачайте три пакета из их последних релизов (используется GitHub CLI; как
   вариант — скачайте их со страницы релизов каждого проекта в браузере):

   ```sh
   mkdir gc2607-debs && cd gc2607-debs
   gh release download v1.0   -R VitalyOstanin/gc2607-driver
   gh release download v1.0   -R VitalyOstanin/gc2607-ipu-bridge
   gh release download v0.2.0 -R VitalyOstanin/gc2607-isp
   ```

2. Установите все три сразу, чтобы `apt` разрешил зависимости и рекомендованные
   пакеты (`v4l2loopback-dkms`, `mesa-vulkan-drivers`) вместе:

   ```sh
   sudo apt install ./gc2607-driver-dkms_1.0_all.deb \
                    ./gc2607-ipu-bridge-dkms_1.0_all.deb \
                    ./gc2607-isp_0.2.0_amd64.deb
   ```

   Два DKMS-пакета собирают и подписывают свои модули ядра под работающее ядро
   серии 7.x (другие серии ядра пропускаются через `BUILD_EXCLUSIVE_KERNEL`).
   Пакет `gc2607-isp` устанавливает `gc2607-video` в `/usr/bin`, конфигурацию
   loopback и сервис `gc2607-camera` (включён для следующей загрузки, но не
   запускается во время установки).

3. Перезагрузитесь, чтобы новый `ipu-bridge` заменил штатный и IPU6 построил
   CSI-2-линк к сенсору. После перезагрузки модуль loopback загружается из
   `/etc/modules-load.d/`, сервис `gc2607-camera` работает, а камера остаётся в
   простое, пока её не откроет приложение.

   ```sh
   sudo reboot
   ```

4. Проверка:

   ```sh
   systemctl status gc2607-camera        # active (running), сенсор в простое
   v4l2-ctl --list-devices               # показывает "MateBook Camera (GC2607)"
   ffplay -f v4l2 /dev/video0            # открытие узла будит камеру
   ```

   Теперь любое веб-камерное приложение (браузер, OBS, `ffplay`) может открыть
   "MateBook Camera (GC2607)" как обычную веб-камеру. Сенсор включается только
   пока приложение ведёт захват, и снова уходит в suspend, когда захват
   прекращается.

   Сессия камеры, переставшая отдавать кадры (типичное состояние после цикла
   сна и пробуждения системы), переоткрывается на месте: узел loopback остаётся
   открытым, поэтому приложение сохраняет устройство и видит паузу, а не
   пропажу веб-камеры. Попытки переоткрытия идут с удвоением задержки; если
   камера остаётся недоступной, демон завершается с ненулевым кодом и его
   перезапускает менеджер сервисов.

Чтобы удалить сервис веб-камеры и конфигурацию loopback, см.
[`packaging/README.md`](packaging/README.md#uninstall); два DKMS-пакета удаляются
командой `sudo apt remove gc2607-driver-dkms gc2607-ipu-bridge-dkms`.

### Сборка из исходников

Чтобы собрать стек из исходников вместо установки готовых пакетов:

- **Офлайн-CLI** (`gc2607-isp`, сырой кадр → изображение, оборудование не нужно) —
  [Сборка и запуск (офлайн CLI)](#сборка-и-запуск-офлайн-cli).
- **Бинарь живой веб-камеры** (`gc2607-video`) —
  [Живая веб-камера](#живая-веб-камера-gc2607-video) для сборки в контейнере или
  [Сборка на других дистрибутивах](#сборка-на-других-дистрибутивах) для нативной
  сборки.
- **Debian-пакет** этого ISP — [Debian-пакет (.deb)](#debian-пакет-deb).
- **Драйвер сенсора и ipu-bridge** собираются из своих репозиториев
  ([gc2607-driver](https://github.com/VitalyOstanin/gc2607-driver),
  [gc2607-ipu-bridge](https://github.com/VitalyOstanin/gc2607-ipu-bridge));
  каждый поставляет DKMS-пакет, собираемый командой `dpkg-buildpackage -us -uc -b`.

## Сборка и запуск (офлайн CLI)

Офлайн-CLI конвертирует сохранённый сырой кадр в изображение. Он нетребователен к
зависимостям и собирается на хосте (libcamera не нужна):

```sh
cargo build --release
./target/release/gc2607-isp [--half|--mhc] <input.bin> [output.png|output.ppm]
```

`input.bin` — сырой кадр SGRBG10 1928x1088, stride 1952 u16/строка.

- `--mhc` (по умолчанию): полноразрешающий debayer Malvar-He-Cutler, выход
  1928x1088.
- `--half`: half-res debayer, 964x544, совпадает с golden-эталоном.

Формат вывода выбирается по расширению: `.png` (через крейт `image`) либо PPM
(P6) в остальных случаях.

## Живая веб-камера (gc2607-video)

`gc2607-video` запускает конвейер вживую: захватывает сырые кадры через libcamera,
выполняет ISP, ведёт автоэкспозицию на сенсоре и публикует обработанные кадры в
узел v4l2loopback, который любое приложение (браузер, OBS, `ffplay`) открывает как
обычную веб-камеру.

### Предусловия

1. Стек сенсора GC2607 загружен и работает: `gc2607.ko` + пропатченный
   `ipu-bridge`, так что среди `/dev/v4l-subdev*` есть субдев `gc2607`, и libcamera
   видит камеру. Физический переключатель камеры должен быть **включён**.
2. Установлен рантайм libcamera 0.7.
3. Для вывода создано устройство v4l2loopback, например:
   ```sh
   sudo modprobe v4l2loopback card_label="MateBook Camera (GC2607)" exclusive_caps=1
   ```
   Запомните созданный узел (по умолчанию проект использует `/dev/video0`).

### Сборка

`gc2607-video` требует фичу `capture` (крейт `libcamera` + clang), поэтому
собирается в контейнере podman (Ubuntu 26.04), а не на хосте. Собирайте с
`capture,gpu`, чтобы бэкенд по умолчанию `auto` мог использовать GPU (фича `gpu`
самодостаточна — wgpu/Vulkan, mesa ANV на Intel iGPU — и не требует
дополнительного рантайма кроме рабочего Vulkan-драйвера):

```sh
# сборка внутри контейнера (образ собирается один раз из Containerfile)
podman run --rm --http-proxy=false \
  -v "$PWD":/work \
  -v gc2607-cargo-registry:/root/.cargo/registry \
  -v gc2607-cargo-target:/work/target \
  localhost/gc2607-isp-build:latest \
  cargo build --release --features capture,gpu --bin gc2607-video

# копирование бинаря из target-тома контейнера на хост
podman run --rm \
  -v "$PWD":/work -v gc2607-cargo-target:/work/target \
  localhost/gc2607-isp-build:latest \
  cp /work/target/release/gc2607-video /work/gc2607-video
```

(Сначала соберите образ, если нужно: `podman build -t gc2607-isp-build:latest -f Containerfile .`)

Чтобы собрать бинарь только под CPU, уберите фичу `gpu` (`--features capture`);
тогда `auto` сводится к CPU-пути, а `--backend gpu` выдаёт ошибку.

#### Почему контейнер

Контейнер нужен только для фичи `capture` — офлайн-CLI и GPU-бэкенд написаны на
чистом Rust и собираются прямо на хосте. Крейту `libcamera` нужны три вещи **на этапе
сборки**, которые проект намеренно держит вне хоста: заголовки libcamera
(`libcamera-dev`), `clang` (крейт `libcamera-sys` генерирует из этих заголовков
свои биндинги через bindgen) и `pkg-config`. Образ несёт их вместе со своим
зафиксированным Rust toolchain; реестр cargo и каталог target смонтированы как
именованные тома, поэтому крейты не перекачиваются и в `~/.cargo` хоста ничего не
пишется. (Сам Rust — не причина контейнера: на хосте уже есть cargo и он
используется для офлайн- и GPU-сборок.)

Образ именно `ubuntu:26.04`, потому что его libcamera (0.7) совпадает с рантаймом
ноутбука `libcamera.so.0.7`: бинарь линкует libcamera **динамически**, копируется
на хост и запускается там против рантайма libcamera хоста (пакет `-dev` на хосте
не нужен). Сборка против другой версии libcamera дала бы бинарь, не совпадающий с
рантаймом хоста.

Если готовы установить `libcamera-dev` и `clang` на сборочную машину, контейнер
можно пропустить и собрать нативно — см.
[Сборка на других дистрибутивах](#сборка-на-других-дистрибутивах).

### Запуск

```sh
./gc2607-video                 # по умолчанию: --backend auto (предпочесть GPU, откат на CPU), full-res 1080p
./gc2607-video --backend cpu   # принудительно CPU-путь (по умолчанию --debayer mhc --threads 8)
```

Затем откройте узел loopback (`/dev/video0`, например "MateBook Camera (GC2607)")
в любом приложении или посмотрите напрямую:

```sh
ffplay -f v4l2 /dev/video0
```

### Флаги

| Флаг | По умолчанию | Назначение |
|------|--------------|------------|
| `--device /dev/videoN` | `/dev/video0` | узел вывода v4l2loopback |
| `--device-label <name>` | (не задан) | искать loopback по его `card_label` вместо фиксированного `/dev/videoN`; перекрывает `--device`. Устойчиво к порядку обнаружения (IPU6 ISYS создаёт десятки узлов `/dev/video*`). Используется systemd-сервисом. |
| `--backend auto\|cpu\|gpu` | `auto` | `auto` предпочитает GPU и откатывается на CPU, если GPU нет. `gpu` принудительно использует GPU (пиксельные стадии как Vulkan compute, AWB на CPU; всегда full-res MHC, игнорирует `--debayer`) и завершается с ошибкой, если инициализация не удалась. `cpu` принудительно использует CPU-путь. GPU требует сборки с фичей `gpu`; без неё `auto` сводится к CPU, а `gpu` выдаёт ошибку. |
| `--debayer half\|mhc` | `mhc` | `mhc` = full-res 1920x1080; `half` = 960x540, легче (только CPU-бэкенд) |
| `--threads N` | `8` | число рабочих потоков ISP (бюджет CPU; см. примечание). На GPU-бэкенде их использует только периодический AWB на стороне CPU. |
| `--no-ae` | (AE включена) | отключить автоэкспозицию (использовать текущие настройки сенсора) |
| `--target <0..1>` | `0.15` | целевая средняя яркость AE, в линейном свете (яркость вывода измеряется с обращённой гаммой sRGB). `0.15` линейных ≈ gamma-кодированный средне-серый `0.43`. |
| `--max-gain <idx>` | `16` | максимальный индекс LUT аналогового усиления для AE |
| `--on-demand auto\|on\|off` | `auto` | открывать камеру и выполнять ISP только пока приложение ведёт захват (см. [План развития](#план-развития)). `auto` сам включается, когда v4l2loopback предоставляет событие client-usage, и иначе стримит постоянно; `on` требует события (предупреждает и откатывается, если его нет); `off` принудительно стримит постоянно. В простое сенсор камеры остаётся в runtime-suspend; producer пишет лишь дешёвые чёрные keepalive-кадры, чтобы потребители могли согласовать формат. |

Производительность (Core Ultra 185H): `mhc` держит 30 fps сенсора на 8 потоках
(~29 на 4); `half` достигает 30 fps на 4 потоках (~27 на одном потоке). Значение
по умолчанию (`mhc`, 8 потоков) максимизирует качество; снизьте `--threads` или
используйте `--debayer half`, чтобы уменьшить нагрузку на CPU и нагрев на
термально зажатом ноутбуке.

GPU-бэкенд выдаёт тот же full-res MHC-результат (проверено против CPU-пути с
точностью до 1 LSB, `tests/gpu.rs`), разгружая пиксельную работу. В одной
фиксированной сцене потребление CPU процессом упало с ~154% (CPU `mhc`, 8 потоков)
до ~37% (GPU) при той же частоте кадров — примерно четырёхкратное снижение нагрузки
на CPU, что важно на этом термально зажатом ноутбуке.

### Устранение неполадок: размытая / полосатая картинка после смены разрешения

v4l2loopback сохраняет формат на стороне захвата, зафиксированный на узле первым.
Если демон запущен один раз в half-res (`--debayer half`, 960x540), а затем в
full-res по умолчанию (`mhc`, 1920x1080) *без перезагрузки модуля*, producer
пишет кадры 1920x1080 в узел, формат захвата которого всё ещё закреплён на
960x540. Потребители тогда снимают укороченные кадры (например, `1026048` байт
вместо ожидаемого размера), что проявляется как низкоконтрастное, размытое
изображение со сдвигом цвета и горизонтальными полосами (рваный кадр), а не как
явная ошибка.

Исправление: перезагрузите модуль, чтобы сбросить формат, затем запустите демон в
нужном разрешении:

```sh
sudo modprobe -r v4l2loopback && sudo modprobe v4l2loopback
```

Чтобы избежать этого, запускайте демон в согласованном разрешении (рекомендуется
full-res `mhc` по умолчанию). Смена `--debayer` между запусками требует
перезагрузки модуля.

### Запуск как системного сервиса (по запросу)

[`packaging/`](packaging/) содержит systemd-юнит и конфигурацию loopback для
запуска `gc2607-video` как сервиса по запросу: виртуальная веб-камера присутствует
всегда, но сенсор и ISP работают только пока приложение ведёт захват. Loopback
создаётся при загрузке с фиксированным `card_label`, и демон находит его по метке
(`--device-label`), поэтому номер `/dev/videoN` нигде не зашит. Телеметрия (stdout)
отбрасывается; предупреждения и ошибки (stderr) попадают в журнал.

Шаги установки и управления, а также усиленный (без root) вариант — в
[`packaging/README.md`](packaging/README.md). Кратко:

```sh
sudo install -m 0755 gc2607-video /usr/bin/gc2607-video
sudo install -m 0644 packaging/modules-load.d/gc2607-loopback.conf /etc/modules-load.d/
sudo install -m 0644 packaging/modprobe.d/gc2607-loopback.conf     /etc/modprobe.d/
sudo install -m 0644 packaging/systemd/gc2607-camera.service       /etc/systemd/system/
sudo modprobe v4l2loopback
sudo systemctl daemon-reload && sudo systemctl enable --now gc2607-camera
```

## Сборка на других дистрибутивах

У проекта три профиля сборки с разными системными требованиями:

| Профиль                                           | Фичи cargo         | Системные зависимости на этапе сборки                                | Зависимости рантайма                                      |
|---------------------------------------------------|--------------------|----------------------------------------------------------------------|-----------------------------------------------------------|
| Офлайн-CLI (`gc2607-isp`)                         | нет (по умолчанию) | только Rust toolchain                                                 | нет                                                       |
| + GPU-бэкенд                                      | `gpu`              | только Rust toolchain (wgpu поставляется в комплекте)                 | рабочий Vulkan-драйвер (Mesa ANV для Intel iGPU)          |
| Живой / захват (`gc2607-video`, `gc2607-capture`) | `capture[,gpu]`    | заголовки libcamera, `clang` (для bindgen), `pkg-config`, C++ toolchain | рантайм libcamera + стек сенсора GC2607 (см. Предусловия) |

Офлайн-CLI и GPU-бэкенд написаны на чистом Rust и собираются на любом
дистрибутиве с актуальным стабильным toolchain; разрабатывались и тестировались
на Rust 1.88.0 (зафиксирован в `Containerfile`). Системные библиотеки нужны
только фиче `capture`.

### Версия libcamera

Крейт `libcamera` (0.7) привязывается к системной libcamera через `pkg-config` и
`bindgen`. Целевыми считаются только текущие релизы каждого дистрибутива, и все
они поставляют libcamera, достаточно новую для крейта (по словам upstream:
«known to build with libcamera v0.4.0 and up»). По состоянию на 2026-06-08, по
данным repology.org:

| Дистрибутив          | libcamera                | Нативная сборка `capture`     |
|----------------------|--------------------------|-------------------------------|
| Ubuntu 26.04 LTS     | 0.7.0                    | да (проверено)                |
| Debian 13 (trixie)   | 0.4.0 (backports 0.7.1)  | должна работать (здесь не проверялось) |
| Fedora 43 / 44       | 0.5.2 / 0.7.x            | должна работать (здесь не проверялось) |

«да (проверено)» отмечает единственную комбинацию, на которой проект реально
собирался и запускался, — образ podman `ubuntu:26.04`, совпадающий с ABI рантайма
libcamera 0.7.0 ноутбука. Остальные строки удовлетворяют требованию крейта
`>= 0.4.0`, но здесь не проверялись; различия API между минорными версиями
libcamera могут потребовать небольших правок.

Установите зависимости сборки, затем собирайте нативно вместо контейнера:

```sh
# Debian / Ubuntu
sudo apt install libcamera-dev clang pkg-config build-essential
# Fedora
sudo dnf install libcamera-devel clang pkgconf-pkg-config gcc-c++

cargo build --release --features capture,gpu
```

### Область применимости по оборудованию

Этот ISP рассчитан на одно конкретное устройство — камеру GC2607 в MateBook X
Pro 2024. Офлайн-CLI переносим (обрабатывает сохранённый сырой кадр на любой
машине), но `gc2607-video` / `gc2607-capture` полезны только на этом ноутбуке, где
присутствуют драйвер сенсора `gc2607`, пропатченный `ipu-bridge` и тюнинг. На
другом оборудовании бинари захвата собираются, но не находят камеры `gc2607` для
открытия.

## Debian-пакет (.deb)

Для Ubuntu 26.04 живая веб-камера упакована как `gc2607-isp` (amd64): устанавливает
`gc2607-video` в `/usr/bin`, systemd-сервис по запросу и конфигурацию loopback
(файлы в [`packaging/`](packaging/)). Бинарь собирается отдельно, и пакет лишь
оборачивает его (`debian/rules` подменяет шаги компиляции пустышками), поэтому
`dpkg-shlibdeps` выводит зависимость `libcamera0.7`, сканируя ELF.

Соберите пакет после того, как существует бинарь:

```sh
# соберите бинарь в контейнере (см. «Живая веб-камера» выше), затем скопируйте его
# в корень репозитория, где его ожидает debian/install:
cp target/release/gc2607-video ./gc2607-video
sudo apt install -y debhelper dpkg-dev          # инструменты упаковки, один раз
dpkg-buildpackage -us -uc -b                     # -> ../gc2607-isp_0.2.0_amd64.deb
sudo apt install ../gc2607-isp_0.2.0_amd64.deb
```

Пакет `Recommends` `mesa-vulkan-drivers`, `v4l2loopback-dkms`, `gc2607-driver-dkms`
и `gc2607-ipu-bridge-dkms`. Он включает `gc2607-camera.service` для следующей
загрузки, но не запускает его во время установки (узел loopback создаётся при
загрузке); см. [`packaging/README.md`](packaging/README.md).

### CI

[`.github/workflows/build-deb.yml`](.github/workflows/build-deb.yml) собирает
бинарь и `.deb` внутри контейнера `ubuntu:26.04` (для совпадения с libcamera 0.7)
на каждый push и pull request и выкладывает `.deb` как артефакт workflow. На теге
`v*` он также прикрепляет `.deb` к GitHub-релизу. Фича GPU компилируется, но не
тестируется в рантайме (на хостовых раннерах нет GPU).

## Проверка корректности (golden)

`cargo test` сверяет Rust-конвейер с проверенным эталоном на Python на
фиксированном кадре:

- `estimate_matches_reference` — gains/CCT/источник LSC совпадают с точностью 1e-3
  (AWB опирается на медиану/перцентиль, чувствителен к порядку операций);
- `render_matches_reference` — детерминированный рендер при заданных gains/CCM/LSC
  совпадает с эталоном побайтно (допуск 1 LSB на нескольких пикселях).

Снимки сенсора и производные от них golden-артефакты приватны для сцены
пользователя и в репозиторий **не** коммитятся (см. `.gitignore`); тюнинг в
`data/` — это данные тюнинга сенсора, а не снимок, и отслеживается. При
отсутствии локальных данных тесты пропускаются, а не падают. Чтобы их запустить,
положите сырой кадр в `tests/data/sample-raw.bin` и сгенерируйте эталон:
`python3 tools/gen_golden.py`.

## План развития

| Этап | Состояние | Содержание |
|------|-----------|------------|
| 1. Ядро CPU (офлайн) | готово | half-res debayer, golden-проверка против Python |
| 2. Качество + CLI | готово | собственный построчно-параллельный MHC-debayer (заменил крейт `demosaic`), вывод PNG |
| 3. Захват | готово | сырые кадры + контролы exposure/gain через крейт `libcamera` (сборка в podman ubuntu:26.04) |
| 4. Петля AE | готово | автоэкспозиция, exposure-priority, метрика в линейном свете, проверено на оборудовании |
| 5. Вывод | готово | запись кадров в v4l2loopback `/dev/video0` |
| 6. Производительность | готово | `Processor` (переиспользование буферов, кэширование AWB/сеток), параллельный front-end + MHC + упаковка YUYV; 30 fps в full-res |
| 7. Разгрузка на GPU | готово | `--backend gpu`: пиксельные стадии (unpack/BLC/LSC/WB, MHC, CCM, гамма, упаковка YUYV) как compute-шейдеры Vulkan; AWB на CPU. ~4x меньше CPU при той же частоте кадров |
| 8. Захват по запросу | готово | `--on-demand auto` открывает камеру + выполняет ISP только пока приложение ведёт захват, по событию `V4L2_EVENT_PRI_CLIENT_USAGE` у v4l2loopback (механизм v4l2-relayd, реализован внутри процесса); в простое сенсор остаётся в runtime-suspend. Откатывается на постоянный стрим там, где события нет |

- [abbood/gc2607-v4l2-driver](https://github.com/abbood/gc2607-v4l2-driver) —
  V4L2-субдев-драйвер GC2607 с питанием через INT3472 и патчем `ipu_bridge`,
  отдающий узел `v4l2loopback` через GStreamer (разрабатывался на Arch). Основа
  для собственного [gc2607-driver](https://github.com/VitalyOstanin/gc2607-driver)
  этого проекта.
- [antonbiluta/gc2607-driver](https://github.com/antonbiluta/gc2607-driver) —
  драйвер GC2607 и патч `ipu_bridge` (Fedora), ещё один ранний ориентир для
  поднятия сенсора.

Затем проект пошёл своим путём — написанный с нуля драйвер сенсора по
рекомендациям ядра для camera-сенсоров, отдельный патч `ipu-bridge` и этот
Rust-ISP с извлечённым заводским тюнингом, — но те проекты показали, что это
возможно и с чего начать.
